# Edge Measurement Format v1 (EMF1)

**Status:** project application-payload standard, version 1. This is a custom Edge Monitor format, not Cayenne LPP and not a LoRaWAN MAC format.

The machine-readable registry is `emf1_registry.json`. It is authoritative for the magic byte, FPort, wire types, common field IDs, aliases and units/scales. Python loads it directly; the browser UI and generic ChirpStack codec registry blocks are generated by `build_emf1_artifacts.py`. Never change one copy alone.

## Payload identification

- **EMF1:** FPort **10**, first payload byte **`0xE1`**.
- **Legacy Fixed6:** FPort 1 and six bytes; receive-only compatibility for currently installed nodes, not a code-generation choice.
- FPort assignments are an Edge Monitor project convention, not a claim that FPort 10 means EMF1 on every LoRaWAN network.

## EMF1 record structure

`E1 [field_id] [type_code] [value bytes] [field_id] [type_code] [value bytes] ...`

All multi-byte values are **big-endian**. A type code defines exact storage width, signedness and numeric scale. There is no separate record-length byte. A decoder may skip an unknown field ID if its type is known, but must reject unknown type codes because it cannot safely find the next record boundary. A header-only `E1` frame is invalid.

Field IDs `0x01`–`0x7F` are reserved for common measurement meanings. IDs `0x80`–`0xFE` are allocated by saved node configuration for custom fields; the field map must be included with the configuration-bound decoder. IDs `0x00` and `0xFF` are reserved. A field ID may occur at most once per uplink. Known common IDs must use their registry-defined wire type. Multiple physical sensors measuring the same semantic value receive distinct IDs after the first registered ID.

## Wire type registry

| Type | Name | Bytes | Decoding rule |
|---:|---|---:|---|
| `0x01` | Boolean | 1 | Only `0` or `1`; decoded false/true |
| `0x02` | Unsigned 8-bit | 1 | unsigned integer |
| `0x03` | Signed 8-bit | 1 | signed integer |
| `0x11` | Unsigned 16-bit | 2 | unsigned integer |
| `0x12` | Signed 16-bit | 2 | signed integer |
| `0x21` | Unsigned 16-bit × 0.1 | 2 | `raw × 0.1` |
| `0x22` | Signed 16-bit × 0.1 | 2 | `raw × 0.1` |
| `0x23` | Unsigned 16-bit × 0.01 | 2 | `raw × 0.01` |
| `0x24` | Signed 16-bit × 0.01 | 2 | `raw × 0.01` |
| `0x31` | Unsigned 32-bit | 4 | unsigned integer |
| `0x32` | Signed 32-bit | 4 | signed integer |

The type describes wire representation, not semantic unit. For instance, `0x23` means %RH only when associated with the humidity field; for a custom field, its selected unit and conversion must be documented in the field map.

## Common field registry v1

| Field ID | Key | Unit / meaning | Wire type |
|---:|---|---|---:|
| `0x01` | `temperature` | °C | `0x24` signed × 0.01 |
| `0x02` | `humidity` | %RH | `0x23` unsigned × 0.01 |
| `0x03` | `moisture` | raw ADC counts, **not calibrated moisture percent** | `0x11` unsigned integer |
| `0x04` | `illuminance_lux` | lux | `0x31` unsigned integer |
| `0x05` | `pressure_hpa` | hPa | `0x21` unsigned × 0.1 |
| `0x06` | `co2_ppm` | ppm | `0x11` unsigned integer |
| `0x07` | `ph` | pH | `0x24` signed × 0.01 |
| `0x08` | `dissolved_oxygen_mg_l` | mg/L | `0x23` unsigned × 0.01 |
| `0x09` | `conductivity_ms_cm` | mS/cm | `0x23` unsigned × 0.01 |
| `0x0A` | `flow_m3_h` | m³/h | `0x21` unsigned × 0.1 |
| `0x0B` | `ammonia_mg_l` | mg/L | `0x23` unsigned × 0.01 |
| `0x0C` | `cod_mg_l` | mg/L | `0x11` unsigned integer |
| `0x0D` | `digital_input` | Boolean input state | `0x01` Boolean |
| `0x0E` | `battery_mv` | mV | `0x11` unsigned integer |
| `0x0F` | `presence` | Boolean presence state | `0x01` Boolean |

`moisture_raw_adc` is an alias for the common moisture concept; only one ID `0x03` can be transmitted in a single frame. If a node has additional moisture sensors, the next physical sensor gets a config-allocated ID while retaining its saved output key.

## Custom fields and generation rules

The wizard requires an explicit wire type for custom fields. The selected wire type's scale applies to the encoded integer: the generated `emfAddValue` helper accepts an engineering value, divides by the scale, rounds, validates the numeric range and writes the resulting integer in big-endian order. Sensor drivers remain responsible for reading, calibration and ensuring the measurement truly uses the field's declared unit.

The configuration-bound `chirpstack_codec.js` embeds the field names for configured custom IDs. The generic codec uses `field_XX` for unknown custom IDs. Bundles include the registry schema and SHA-256 fingerprint so mismatched registry versions can be detected.

## Reference vector

Temperature `28.80 °C`, humidity `32.00 %RH`, raw moisture ADC `0`:

`E1 01 24 0B 40 02 23 0C 80 03 11 00 00`

The decoder returns `temperature: 28.8`, `humidity: 32`, and `moisture: 0`.

## Legacy receive-only compatibility

Old nodes may still transmit Legacy Fixed6 on FPort 1. The backend and ChirpStack codec retain a decoder for those already-installed nodes while migration is pending, but the wizard rejects that format, emits only EMF1 scaffolds and bundles, and refuses bundles declaring any other payload format. A dashboard/profile change does not reflash or otherwise alter a node.

## Validation requirements

- Reject truncated record headers/values, invalid Boolean values, unknown types, duplicate IDs and invalid common-field type codes.
- Preserve raw hex, FPort, decoded field map and decoding errors in diagnostics.
- Keep sensor IDs, field IDs and decoded output keys stable when adding fields/modules to a saved configuration.
- Check the active regional/data-rate maximum before adding many records; the scaffold's buffer ceiling does not guarantee that a particular LoRaWAN data rate can transmit a payload of that size.
- Never allow sensor code generation to edit or remove the fixed WLAN OTA maintenance core.
